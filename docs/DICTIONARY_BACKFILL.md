# Перенос структуры БКРС в существующие записи

Новый API умеет отдавать структурированные статьи, примеры, ссылки и оформление.
Для старых записей нужны исходные DSL-статьи: одна миграция добавит колонки, но не
восстановит утраченную разметку. Этот инструмент дополняет существующие строки,
сохраняя их `id`, `hanzi`, `pinyin`, `ru`, `pos`, `examples` и последовательность ID.

## Границы

- Обрабатываются только статьи БКРС. Обратный словарь БРуКС остаётся без изменений.
- Совпасть должны все пять старых полей, включая прежний HTML в `examples`, а не
  только слово. Одинаковые дубликаты источника допустимы. Разные исходные статьи,
  дающие одинаковые старые поля, считаются неоднозначными и пропускаются.
- `raw_dsl` и `article` заполняются только когда оба поля SQL NULL. Уже полностью
  совпадающие данные считаются готовыми. Иные заполненные данные не заменяются.
- Нет вставок, удаления строк, очистки таблиц, изменения ID или переноса локальной
  базы на сервер. `scripts/local_full_dictionary.py` не является способом выпуска.
- Нет автоматической загрузки `.env` и импорта настроек приложения. Соединение
  использует только явно заданные переменные процесса `DB_HOST`, `DB_PORT`,
  `DB_NAME`, `DB_USER`, `DB_PASSWORD`, либо имя переменной DSN через `--dsn-env`.
  Значения паролей и DSN не печатаются и не сохраняются в артефактах.
- Версия, размер и SHA-256 каждого исходного файла сохраняются в каталоге.
  Если сервер содержит другую версию словаря, часть строк не совпадёт. Покрытие
  определяется только серверным dry-run; локальная проверка его не гарантирует.

## До серверного запуска

Проверить фактическую схему/ревизию Alembic, текущий код/образ, Compose-конфигурацию,
версию источника, число записей и свободное место. В старой миграции проекта есть
заметка о почти заполненном серверном диске; это историческая информация, а не
проверка текущего состояния. Нужен запас на полный резервный dump, каталог,
план, журнал, новые текстовые/JSON-данные, PostgreSQL WAL и новый Docker-образ.
Размер каталога можно измерить после его локального создания; полный перенос
нельзя начинать при неизвестном запасе места.

Сначала сделать резервную копию БД и подтвердить её восстановление в отдельную
базу. Сохранить прежний код/образ и конфигурацию. Не останавливать и не удалять
серверный том БД. Применить аддитивную миграцию
`20261115_add_article_structure` **до запуска нового backend**: новый ORM выбирает
обе колонки, поэтому без миграции обычные запросы будут падать. Старый backend
может работать с добавленными nullable-колонками.

Ниже шаблоны интерфейса инструмента, а не готовые команды конкретного сервера.
Фактический путь, интерпретатор, контейнер, переменные и имя базы нужно взять из
проверенной серверной конфигурации. Пароли не следует вставлять в командную строку.

## 1. Каталог исходника — без соединения с БД

Запускать из корня backend. Каталог источника должен содержать четыре физических
UTF-16 файла: `dabkrs_1.dsl`, `dabkrs_2.dsl`, `dabkrs_3.dsl`, `dabruks.dsl`.
Каждый читается один раз; `#INCLUDE` проверяется, но не дублирует загрузку.

```bash
python scripts/backfill_articles.py catalog \
  --source-dir /absolute/path/to/dictionary-data \
  --output /absolute/private/path/catalog.sqlite
```

Это может выполняться локально, до работ с сервером. Каталог содержит исходный
текст и результат разбора. Файлы проверяются хешами до и после чтения. Повторный
запуск не перезаписывает существующий файл: выбрать новый путь. Незавершённый
каталог нельзя использовать. Для полного словаря потребуется время и место.

## 2. План — только чтение серверной БД

```bash
python scripts/backfill_articles.py plan \
  --catalog /absolute/private/path/catalog.sqlite \
  --output /absolute/private/path/plan.sqlite

python scripts/backfill_articles.py inspect \
  /absolute/private/path/plan.sqlite --kind plan
```

План использует read-only repeatable-read транзакцию. Он сохраняет ID подходящих
строк, исходные значения nullable-полей, хеш каталога и отпечаток БД: endpoint
без пароля, имя/пользователь, адрес сервера, OID, число записей и хеш контрольных
старых строк; идентификатор PostgreSQL-кластера добавляется при доступе к нему.
Проверить количества `ready`, `already_current`, `no_exact_source`,
`ambiguous_source`, `populated_conflict`. Низкое покрытие требует разбора причин,
а не ослабления правил совпадения. Структурированная статья может оставаться NULL
для неизвестной разметки; исходный текст при этом сохраняется.

Чтение всего словаря создаёт I/O-нагрузку и держит снимок транзакции. Проводить
проверку в подходящее время; это не нагрузочное тестирование production.

## 3. Применение утверждённого плана

```bash
python scripts/backfill_articles.py apply \
  --catalog /absolute/private/path/catalog.sqlite \
  --plan /absolute/private/path/plan.sqlite \
  --journal /absolute/private/path/journal.sqlite \
  --confirm-database ACTUAL_DATABASE_NAME
```

Только эта явно выбранная команда меняет данные. По умолчанию партия — 200 строк;
допустимый `--batch-size` от 1 до 5000. В каждой транзакции строки блокируются,
сверяются со старым содержимым, после UPDATE повторно проверяются. Меняются только
`raw_dsl` и `article`. Прежние поля, ID и количество строк остаются прежними.

Журнал с исходными значениями сохраняется и синхронизируется **до** коммита БД.
План и каталог удерживаются в SQLite read snapshot, запрещающем параллельный
коммит изменений входных артефактов. Не редактировать и не заменять их файлами.
Артефакты создаются с правами 0600; хранить в приватной директории, вне Git и вне
Docker build context. Не удалять их после выпуска.

После прерывания повторить ту же команду с тем же журналом. Уже применённые строки
распознаются, а неожиданно изменённые данные вызывают STOP. Ранее закоммиченные
партии при STOP остаются применёнными — для их отмены служит журнал. Изменение
идентичности БД, числа записей или контрольных старых строк блокирует продолжение
apply; сначала выяснить причину, не обходить проверку вручную.

## 4. Откат только данных этого переноса

```bash
python scripts/backfill_articles.py rollback \
  --catalog /absolute/private/path/catalog.sqlite \
  --plan /absolute/private/path/plan.sqlite \
  --journal /absolute/private/path/journal.sqlite \
  --confirm-database ACTUAL_DATABASE_NAME
```

Откат восстанавливает ровно исходные nullable-поля из журнала, если текущие поля
ещё совпадают с результатом нашей записи. Позднейшие ручные изменения не затирает.
Отдельно добавленные или отредактированные посторонние строки не мешают откату;
идентичность БД и каждую затронутую строку инструмент всё равно проверяет.
Повторный откат безопасен. При конфликте партия откатывается целиком, ранее
отменённые партии остаются отменёнными. Полный dump остаётся дополнительным
способом восстановления при иных повреждениях БД.

Для отката к прежнему backend не нужно удалять новые колонки. `alembic downgrade`
их удаляет вместе с сохранённой разметкой и не является стандартным откатом
этого выпуска.

## Проверка выпуска

После переноса проверить health, поиск и карточки `你好`, `你`, `打扰`, `什么`,
ссылку `妈逼 → 妈屄`, сложные статьи и старый iOS-клиент. Сверить ID контрольных
записей, число строк и отсутствие изменения старых полей. Затем переключать
backend на подготовленный образ и проверять через внешний HTTPS. Новую iOS-сборку
передавать Apple после проверки согласованной серверной версии.

Инструмент проверен offline тестами и отдельной небольшой PostgreSQL-базой:
аддитивная миграция, dry-run, дубликаты/неоднозначность, конфликт, сбой после
коммита БД до записи статуса журнала, возобновление, точный откат и отказ затереть
позднейшие правки. Полного backfill действующей серверной БД ещё не было.

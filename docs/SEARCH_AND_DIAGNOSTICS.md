# Русские статьи, поиск и диагностика

Выпуск включает изменения backend и iOS 1.0.1 (4). Публикация кода в GitHub
не применяет backfill к действующей базе. Развёртывание backend и восстановление
структуры старых записей выполняются отдельно по инструкции ниже.
Настройки API, ключей, TLS и таймаутов в этом выпуске не меняются.

## Почему результаты отличались от Dicty

В БРуКС заголовок статьи — русское слово. Старый импорт сохранял только первый
китайский фрагмент в `hanzi`, русский заголовок в `ru`, а полный текст — в
`examples`. Представление API не использовало этот полный текст. Список iOS
показывал первый китайский фрагмент как самостоятельный заголовок, а поиск
мог объединять разные русские статьи по этому фрагменту.

Пример: исходная статья «привет» начинается с `敬礼 jìnglǐ, 问候 wènhòu`, содержит
примеры, а вторым значением даёт `你好 nǐhǎo`. Простая замена 敬礼 на 你好 скрыла бы
значения исходника. Новое поведение сохраняет русский заголовок и всю статью.
«Плохо» аналогично сохраняет 坏, 不好 и остальные значения с примерами.

Местный источник называется **БРуКС — 250920**. На скриншотах Dicty — **260610**.
Это разные версии данных; исправление не заменяет источник на версию Dicty.

## Что изменилось

- Импортёр сохраняет исходный DSL и структурированную статью с явным
  `article.source` для БРуКС. Статьи, состоящие из ссылок, больше не требуют
  выдуманного китайского заголовка при новом импорте.
- API добавляет необязательные `headword` и `headword_language`. ID и прежние
  поля сохраняются. Китайская статья с коротким русским переводом не объявляется
  русской исходной статьёй по эвристике.
- Русский поиск сначала выдаёт точный исходный заголовок, затем его продолжения,
  затем совпадения в переводах. Одинаковые копии статьи объединяются; разные
  русские статьи с одним первым китайским переводом остаются разными.
- Для отдельного запроса «Россия» существующая статья 俄罗斯 — éluósī получает
  приоритет перед сочетаниями вроде «Россия и Белоруссия» и вариантом 俄国.
  Регистр и пробелы не влияют на это правило; поиск полной фразы не меняется.
- Ранжирование и выбор ограниченного результата выполняются в PostgreSQL.
  Пиньинь больше не зависит от первых 50 000 ID и не загружает их полные статьи
  в Python. Нормализация SQL ограничена семейством первой буквы.
- Поиск в середине текста выполняется только при отсутствии прямых результатов.
  Русский fallback учитывает границы слова и не запускается для запросов короче
  трёх букв. Китайский поиск и словарный контекст ИИ предпочитают китайские
  исходные статьи обратным русским статьям с тем же `hanzi`.
- iOS показывает русский заголовок и до трёх строк статьи в списке, полную
  структуру в карточке. Скрыты пиньинь и порядок черт первого китайского фрагмента
  у русских статей. История и избранное сохраняют новую информацию; открытие
  старого избранного обновляет его данные без изменения позиции или состава.
- Отменённый или устаревший поиск не перезаписывает новый результат.

## Диагностика

Backend присваивает запросу UUID, возвращает `X-Request-ID` и записывает событие
`http_request` с методом, шаблоном маршрута, статусом и длительностью. Новая
запись не содержит поисковый текст, query string, тело, IP клиента или ключи.
Входящий request ID не принимается на доверии. Необработанный 500, сформированный
внешним обработчиком Starlette, может не содержать заголовок, но событие 500
остаётся в журнале. Существующие access logs Caddy/Uvicorn не перенастраивались.

iOS различает таймаут, отсутствие сети, TLS, сертификат и HTTP-ошибку. Показывает
числовой код и, если получен корректный UUID, request ID. При сетевом таймауте
до получения ответа ID на телефоне может отсутствовать. Это диагностическое
улучшение, а не доказательство устранения российского сетевого инцидента.

`/api/health` по-прежнему проверяет только работу HTTP-приложения. Успех health
не доказывает работоспособность базы, поиска или AI-провайдера.

### Безопасный серверный отчёт

Запускать `scripts/diagnose_server_readonly.py` **на сервере** с правами чтения
журналов. Он читает ограниченные окна Caddy и OOM, текущую память/диск/нагрузку
и выполняет два GET health. Ничего не меняет и не перезапускает.

Из Mac можно передать скрипт через stdin, не сохраняя его на сервере:

```bash
ssh -o ConnectTimeout=10 root@31.129.45.131 'python3 -' \
  < scripts/diagnose_server_readonly.py
```

Если SSH использует другого пользователя, заменить `root` его именем. Для этого
пользователя нужны права на журналы; пустой отчёт без таких прав не является
подтверждением отсутствия ошибок. Ранее порт 22 не отвечал, поэтому возможен
таймаут. Альтернатива — перенести файл через консоль Selectel и выполнить там:

```bash
sudo python3 /путь/diagnose_server_readonly.py
```

После развёртывания middleware можно добавить `--backend-container ИМЯ` для
реального имени контейнера backend. Без этого параметра Docker-логи не читаются.
С ним читаются только ограниченные выборки указанного контейнера; выводятся
строго разрешённые поля нового события, сырые логи не печатаются.

Окно происшествия: 23 ноября 2026, 00:17–00:23 UTC (22 ноября 19:17–19:23 Нью-Йорк).
Также проверяются последние 30 минут. Отсутствие записей может означать
отключённые, файловые или уже удалённые логи. Текущие ресурсы не восстанавливают
прошлую нагрузку; серверная проверка HTTPS не воспроизводит российский маршрут.

## Уже существующие данные: нужен отдельный backfill

Один выпуск кода не восстановит утраченную структуру прежних записей. Новый
инструмент дополняет только `raw_dsl` и `article`, когда оба поля SQL NULL и
совпали **все пять** старых полей. Не вставляет и не удаляет записи, не меняет ID.
Не надо заново запускать полный импорт: старый импортёр может создать дубликаты.

Общие требования, резервная копия и гарантии журнала описаны в
[DICTIONARY_BACKFILL.md](DICTIONARY_BACKFILL.md). Сначала проверить на копии базы.
Используются существующие колонки из миграции `20261115_add_article_structure`;
новой миграции в этой работе нет. Состояние схемы production не проверено.

Из корня backend, интерпретатором с зависимостями проекта:

```bash
# Без подключения к БД. Папка private-backfill должна быть вне Git/build context.
python scripts/backfill_articles.py catalog --reverse-only \
  --source-dir /путь/к/data --output /private-backfill/bruks-catalog.sqlite

# Только чтение БД. Требует явно настроенных DB_* переменных или --dsn-env.
python scripts/backfill_articles.py plan \
  --catalog /private-backfill/bruks-catalog.sqlite \
  --output /private-backfill/bruks-plan.sqlite

python scripts/backfill_articles.py inspect /private-backfill/bruks-plan.sqlite --kind plan
```

Пути — шаблоны, не готовые пути сервера. Исходная папка должна содержать все четыре
проверяемых DSL-файла; reverse-only обрабатывает статьи только из `dabruks.dsl`.
Файлы каталога/плана создаются исключительно, существующие не перезаписываются.
Пароль/DSN не вводить аргументом команды и не присылать в чат. `.env` автоматически
не загружается; `--dsn-env` ожидает имя уже заданной переменной с PostgreSQL URL.

Отдельное осознанное применение **после** просмотра плана и проверки копии:

```bash
python scripts/backfill_articles.py apply \
  --catalog /private-backfill/bruks-catalog.sqlite \
  --plan /private-backfill/bruks-plan.sqlite \
  --journal /private-backfill/bruks-journal.sqlite \
  --confirm-database ФАКТИЧЕСКОЕ_ИМЯ_БАЗЫ
```

Журнал сохраняет значения до изменения. Для отката той же операции заменить
`apply` на `rollback` с теми же параметрами. Позднейшие чужие изменения не
затираются. При остановке уже завершённые партии остаются применёнными; их
отменяют через журнал. Ни apply, ни rollback на рабочей базе здесь не выполнялись.

## Что проверено и что осталось проверить

- Полный offline набор backend: **165 обнаруженных тестов, 147 прошли, 18 SQL-тестов
  пропущены без тестового DSN**. Полный набор с отдельной локальной PostgreSQL 16:
  **165/165**, включая все 18 SQL-тестов. Поисковый набор: **25/25**.
- Реальные статьи «привет», «плохо», «плохой», «приветствие», «кот», «здравствуйте»,
  «приветик»: заголовки, примеры, ссылки, дубликаты, границы слова и поздний
  пиньинь после 50 000 ID. Никакого подключения к production в этих тестах.
- На всех **254 454** физических статьях БРуКС реконструкция старого импорта
  совпала с историческим алгоритмом. **245 284** физические статьи допускают
  консервативный backfill; в каталоге **245 283** уникальные сигнатуры.
- **349** ранее импортируемых статей неподдержанного формата пропускаются.
  Ещё **8 821** физическая статья не имела старой импортируемой записи; backfill
  не создаёт их. Новая версия импортёра умеет сохранить поддерживаемые статьи
  без китайского фрагмента при будущем импорте, но это отдельная работа с данными.
- Репетиция с семью строками в отдельной PostgreSQL: четыре изменены, остальные
  корректно классифицированы; повторное применение — ноль изменений; откат
  вернул все строки точно в исходное состояние. ID и старые поля неизменны.
- iOS: настоящие ответы backend для четырёх статей декодируются; все абзацы
  сохраняются через историю/избранное. Прошли сетевые и прежние article-тесты,
  полная Release-сборка generic iOS Simulator без подписи и проверка собранного
  приложения. Временный режим просмотра из файла удалён. Проверены версия,
  production-адрес, privacy manifest и все 9574 ресурса порядка черт с лицензиями.
  Подпись для устройства и загрузка в App Store этой проверкой не охвачены.
- На синтетических 100 001 строке русский prefix использовал существующий индекс.
  Китайский prefix и пиньинь всё ещё могут сканировать таблицу. Это не измерение
  скорости на многомиллионной production-базе; перед выпуском нужны её планы и
  замеры репрезентативных запросов.

Для ручной проверки: русский заголовок «привет», оба значения с 你好, все примеры
«плохо», отсутствие склейки «плохо»/«плохой», китайский 你好, пиньинь nihao,
старое избранное после открытия карточки, поиск без сети и быстрые последовательные
поиски. Сравнивать только после восстановления данных тестового backend.

Адрес iOS по-прежнему production. Одна сборка iOS сейчас не покажет восстановленные
данные до backfill/deploy соответствующего backend. Для предварительного просмотра
использовать тестовую копию backend и отдельную локальную конфигурацию iOS;
не переносить тестовый адрес в релиз. Региональный сбой остаётся неподтверждённым
по первопричине до получения серверного отчёта и повторения на российской сети.
